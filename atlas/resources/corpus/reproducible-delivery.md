# 可复现交付：干净环境里一键跑通才算数

一个 AI 系统"在我机器上能跑"没有意义。可复现交付的判据只有一条：把仓库克隆到一台干净的机器上，执行文档里写的那一条命令，全流程通过。

## 三层证据

第一层是单元测试。每个模块的算法不变量必须被断言。不变量指的是"只要实现正确就必然成立"的性质，例如编码解码往返一致、概率质量归一、凸目标函数单调不增、梯度与数值差分一致。断言精度而不只是断言"不抛异常"。

第二层是端到端测试。用子进程把服务拉起来，轮询健康检查直到就绪，然后依次打成功流和每一条错误流，逐条断言状态码与响应体，最后在 finally 里回收子进程。注意 Windows 上必须用 taskkill 加进程树参数，否则端口泄漏会让下一次运行直接失败。

第三层是确定性复现。同一份输入、同一个随机种子跑两次，结果必须逐位一致。这一层最容易被忽略，也最能暴露隐藏的不确定性来源。

## 不确定性来源清单

哈希函数。Python 内置的 hash 对字符串按进程加盐，同一个词在不同进程里散列到不同桶。任何基于哈希的特征工程都必须换成稳定的摘要算法，例如 BLAKE2b。

字典与集合的遍历顺序。依赖插入顺序不够，必须显式排序或者记录首次出现顺序作为次级键。

浮点求和的顺序。并行归约的求和顺序会改变末位，凡是跨线程聚合的指标都要固定归约顺序。

时间与随机源。评估结果里不要混入墙钟时间，延迟指标单独统计，判定通过的阈值不要依赖它。

## 依赖锁定

顶层依赖钉死精确版本写在 requirements 文件里。除此之外还要产出一份完整闭包清单，由干净虚拟环境安装顶层依赖后冻结得到。这份闭包清单才是"已验证可安装"的证据，因为它包含了全部传递依赖。

生成闭包时要注意平台差异。在 Windows 上冻结出来的清单可能包含 Windows 专有包，例如 pywin32 相关项。如果交付物还要在 Linux 容器里构建，必须把这些包剔除，否则容器构建会在安装阶段失败。

不要把包索引地址写进锁文件。如果安装时使用了镜像源，提交前要把解析地址重写为官方源，完整性哈希不变，但可移植性大幅提升。

## 交付核对

提交前逐条核对：源文件清单是否与预期一致，是否误入调试脚本和临时日志；所有产出是否扫描过禁用字符；文档里的每一条命令是否真的执行过；README 里的路径与仓库实际结构是否一致。
